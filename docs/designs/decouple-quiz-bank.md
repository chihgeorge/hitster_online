# Eng Review: Decouple the Quiz Bank from Room Setup

Generated by /plan-eng-review on 2026-09-22
Branch: main
Repo: chihgeorge/hitster_online

## Problem Statement

Creating or editing a playlist/quiz (timeline mode or Lyrics mode) only happens inside
the room-setup flow (`app/room/[code]/host/page.tsx`), which requires first creating a
room. A host who wants to prep game night content ahead of time — a different day,
possibly a different device than the one they'll host from — has no way to do that.
Modeled on the `critical-answer` repo's `app/bank-editor` + `BankStore` pattern: a
standalone page, decoupled from any room, for authoring quiz content.

## What already exists (reuse, not rebuild)

- `party/playlist.ts`: full CRUD (POST/GET/PUT/DELETE) for a single playlist, Durable
  Object per playlist keyed by UUID, `ownerHostId`-gated, zero dependency on a room.
- `components/PlaylistEditor.tsx`: room-agnostic presentational table editor for the
  *manual* editing path (props: `playlistId`/`songs`/`hostId`/`partyKitHost`).
- `lib/device-id.ts`'s `getOrCreatePersistedId`: existing hostId identity mechanism,
  reusable as-is for a room-less page.
- `lib/ai-metadata.ts`, `lib/lyrics-resolver.ts`: the AI resolution primitives
  themselves, already extracted and reusable.

## Constraints (found by outside-voice review — see below)

- **AI chat-to-diff editing is NOT reusable as-is.** `PlaylistEditor`'s `onProposeEdits`
  callback is wired, today, only to the room's WebSocket (`PROPOSE_EDITS`/
  `PROPOSE_LYRIC_EDITS`, handled in `party/index.ts`'s `handleProposeEdits`/
  `handleProposeLyricEdits`, gated by `authorizeHost` against `this.state.hostId`).
  `party/playlist.ts` has no equivalent action.
- **`party/playlist.ts` is HTTP-only** (`onConnect(_conn) {}`, explicit "No WebSocket
  needed" comment) — cannot stream progress or support cancellation the way the room's
  WebSocket-based `handleLoadPlaylist` does today.
- **Cross-party DO calls are unused in this codebase** but are a real, supported
  PartyKit primitive (`room.context.parties`, confirmed in
  `node_modules/partykit/server.d.ts`) — new ground for this repo, not for the platform.
- Existing hosts already have playlists saved *only* in browser localStorage
  (`hitster_playlists` key) — any change to the room-setup panel's source of truth
  must not silently drop them.

## Decision ledger

### D1: Where does resolve-from-URL logic live, and what's the standalone-page UX?
**Approved:** Extract to `lib/playlist-resolver.ts` (platform-agnostic, same split
discipline as `critical-answer`'s `BankStore`). `party/index.ts`'s 3 existing call
sites (`handleLoadPlaylist`, `handleStartGame` fallback, `handleStartLyricsGame`) and a
new `RESOLVE_FROM_URL` HTTP action on `party/playlist.ts` all call it. No new
runtime/deploy target — secrets stay in PartyKit env only.
Standalone-page UX: **blocking request, single spinner** — no progress streaming, no
cancel. Accepted risk: a large playlist could approach a request timeout; cap the
standalone page's max playlist size below the room's, and verify actual worst-case
duration before shipping (Implementation Task, see below).

### D2: Cross-device playlist library
**Approved: keep in scope.** New hostId-keyed Durable Object (`party/library.ts`)
storing `{playlistId, name, songCount}` per host, replacing localStorage as the source
of truth for both the new standalone page and the existing room-setup Saved Playlists
panel.

### D2a: Two-DO write consistency
**Approved:** `party/playlist.ts`'s POST/DELETE handlers call `party/library.ts`
server-side via `room.context.parties` — one client request triggers both writes.
Accepted gap: Durable Objects don't support cross-DO transactions, so a library-write
failure after a successful playlist-write can still orphan an entry; needs a
self-heal path (e.g., a library read that's missing an entry the client expects
triggers a background reconcile) rather than a hard guarantee. Flagged as an
Implementation Task, not fully designed here.

### D2b: Migration of existing localStorage-only playlists
**Approved:** One-time, silent, idempotent client-side import — first load of either
the room-setup panel or the new standalone page post-deploy POSTs each localStorage
entry into the new library index if not already present. localStorage itself is left
untouched (not cleared), acting as a fallback if the import partially fails.

### D3: Embeddability-filter inconsistency (found during Architecture review)
**Approved: fix.** `handleStartGame`'s fallback path currently skips the
embeddability filter `handleLoadPlaylist` applies. The extracted
`lib/playlist-resolver.ts` always filters — this is an intentional behavior change on
that one call site, needs its own updated test assertion (not a silent diff).

### D4: AI chat-to-diff editing on the standalone page
**Approved: build a 3rd implementation.** A new HTTP action on `party/playlist.ts`
mirrors `handleProposeEdits`/`handleProposeLyricEdits`'s logic as a stateless
request/response instead of a WebSocket send/reply. Explicitly flagged risk (recorded,
not blocking): this recreates one level up the exact 3x-duplication problem this review
exists to fix, and the user has separately requested a visual/UX redesign of this same
chat-to-diff UI — building full parity now risks redoing this specific piece again
right after that redesign lands. Accepted anyway for host-experience consistency.

**Approval readiness: PASS** — D1, D2, D2a, D2b, D3, D4 all have an actual answer
recorded above (AskUserQuestion, this session, 2026-09-22).
