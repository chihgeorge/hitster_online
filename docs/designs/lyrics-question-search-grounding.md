## Problem Statement

Lyrics Mode's question generation (`lib/lyrics-resolver.ts`) already grounds itself in real lyrics — fetched from lrclib.net since v0.4.1 — and asks Claude to pick "a memorable couplet" and blank one phrase from it. That pick is entirely the model's own judgment: nothing tells it which line real listeners actually remember versus which line is just structurally convenient to blank. The host has noticed this feels arbitrary sometimes.

## What Makes This Cool

Grounding the pick in a real popularity signal — not a better-worded prompt asking the model to guess harder at "memorable," but an actual external signal about what people sing along to. The host's own words: "needs the real popularity signal to feel like the idea" — a sharpened prompt that produces the same *kind* of output the app already ships today doesn't count, even if it's technically an improvement.

## Constraints

- App's real catalog is Mandopop/C-pop-heavy (Traditional Chinese output required, CJK-specific blank-length rules) — any external signal source has to actually cover this catalog, not just Western/English pop.
- Hobby project, no monetization — cost and maintenance burden matter more than completeness.
- Existing generation path (`resolveLyricsBatch` in `lib/lyrics-resolver.ts`) batches 10 songs into one Anthropic call today; whatever ships has to either fit that shape or deliberately diverge from it with a stated reason.

## Premises

1. Today's blank-selection is ungrounded in any external popularity signal — **agreed**.
2. Genius.com's API is real and reachable (search, song lookup, "referents" — annotated lyric fragments with vote/scoring data) — **agreed**, confirmed via [Genius API docs](https://docs.genius.com/).
3. Genius's annotation coverage is a dead end for this app's actual catalog — **confirmed by evidence, not just asserted**: two independent web searches explicitly naming genius.com plus the catalog's single biggest hit (告白氣球 by Jay Chou, the most famous song in `party/index.ts`'s `CPOP_SEED`) returned zero Genius.com results.
4. Any real fix needs a fallback to today's method whenever the signal source doesn't deliver — **agreed, and broadened during review (R1-2)**: this covers not just an empty result, but any fetch failure (network timeout, malformed response, rate-limit/quota error). All of these resolve the same way: fall back to today's ungrounded pick for that song, never error or block the playlist load.
5. Whatever signal source is used, it's a new dependency with its own cost/reliability profile — worth minimizing surface area given constraint #2.

**Rejected during the session:** Genius annotations (premise 3 killed it). YouTube-comment mining (real option — reuses the existing YouTube Data API v3 integration, zero new dependency — but more implementation work than what got chosen, and comment noise makes fragment-extraction harder than search-tool grounding). Musixmatch API (broader C-pop lyrics-industry coverage than Genius, but requires applying for partner API access — too slow/uncertain for a hobby project).

## Approaches Considered

### Approach A: Batched call + visibility flag
Add the `web_search` tool to the existing 10-song batched Anthropic call; add a `searched: boolean` per song to the response schema so the reliability gap is visible, not silent. Effort S, risk Medium — cheapest real integration, but the subagent's core worry (one model turn juggling search across 10 songs) ships on purpose, only made observable.

### Approach B: Per-song isolated calls
Branch `resolveLyricsBatch` — search-enabled path fans out one Anthropic call per song, parallelized via the `MAX_CONCURRENT=4` pattern already used elsewhere in this file; non-search path keeps today's batch untouched. Effort M, risk Low — directly fixes the reliability flaw, reuses an existing concurrency pattern from the same file, but multiplies the API call count per playlist load (same total dollar cost, more surface for rate-limit/timeout issues).

## Recommended Approach

**Approach C: Pre-fetch and inject, no model tool-use during generation.** Do a deterministic search/fetch step *before* the batched call, inject the result as grounding text — the exact same shape as how real lyrics from lrclib.net are already injected today (fetch first, pass as context, model never "decides" whether to search).

**What's decided vs. not (added during review, R1-1/R1-3/R1-7):** the *shape* is decided — fetch-then-inject, no model-directed search. The *mechanism* — what the pre-fetch step actually calls — is NOT decided; every structured, vote/popularity-scored source explored this session (Genius referents, Musixmatch) was rejected, so nothing concrete currently remains except a general web search. Provisional candidate, to be confirmed or replaced by the spike (Next Steps step 1-2): a targeted web search per song (e.g. `"<title>" <artist> 最有名一句歌詞` / "most iconic lyric") via `WebSearch` or `WebFetch`, read for a quoted line if one clearly recurs across results. Effort M. **Risk: provisional, not yet substantiated** — cannot be rated Low with confidence until the fetch mechanism is chosen and the caveat below (R1-6) is resolved; treat this approach as approved in shape only until the Open Question closes.

Chosen over A and B because it's the only option that fully closes the reliability gap the subagent flagged AND reuses this file's own established architecture (`lyrics-fetcher.ts` → `lyrics-resolver.ts`'s fetch-then-inject pattern) instead of introducing Anthropic's tool-use mechanism into this codepath for the first time. "Model decides when to search" is exactly the ambiguity that made A and B each carry a real flaw; C removes the ambiguity by never handing the model that decision — but see the Open Question and R1-6 below: this doesn't yet guarantee the fetch actually returns a genuinely external signal rather than more prose for the model to interpret.

## Open Questions

- **What does the pre-fetch step actually fetch?** Not resolved this session — a general web search (see Recommended Approach's provisional candidate) is the only plausible remaining option since every structured source explored was rejected, but this is real design work, not a parameter add. First thing to nail down before writing any production code.
- **Does the chosen fetch source actually deliver an external signal, or just more text to interpret? (R1-6, added during review)** General web search results are prose — the model still has to read them and judge what's "the popular line," which risks landing back at "the same kind of output the app already ships today" (the exact outcome ruled out in What Makes This Cool). When resolving the fetch-mechanism question above, explicitly check whether the result is structured enough to trust, or decide how much residual interpretation is acceptable.
- Game-outcome feedback (log real guess-correctness/speed, use it as a slower-building second signal) — explicitly scoped out of this round, not rejected. Worth its own /office-hours session later if this ships and the host wants a v2.

## Success Criteria

- A blanked phrase is grounded in a real external signal about what listeners actually remember, not just the model's own read of the lyrics text.
- When the signal source has nothing for a song (expected to happen sometimes, especially for Mandopop), the song falls back to today's method — never a broken or empty question.
- No silent ambiguity in the output about whether a given song's pick was actually grounded or fell back — matches the subagent's flagged concern.

## Distribution Plan

Existing deployment pipeline covers this — no new distribution channel, ships as part of the normal Vercel + PartyKit deploy.

3. **Design the pre-fetch step's call shape to avoid Approach B's own rejected problem (R1-5).** Per-song fan-out ahead of the existing 10-song batched Anthropic call reintroduces the same rate-limit/timeout surface Approach B was marked down for. 4. Wire the pre-fetch step into `lib/lyrics-fetcher.ts` (or a sibling module) and inject its result into `resolveLyricsBatch`'s existing prompt-building step in `lib/lyrics-resolver.ts`, same shape as the current lrclib.net injection. Any fetch failure (empty, error, timeout, rate-limit — R1-2) falls back to today's ungrounded pick for that song.
5. Add "was this grounded" visibility to the per-song result for debugging (even Approach C should record this, not just Approaches A/B).

### R2-1 — clarity

**Problem**

> The provisional fetch mechanism's extraction step — 'read for a quoted line if one clearly recurs across results' — doesn't specify whether that reading/matching is deterministic (e.g., regex/frequency matching across search-result snippets) or performed by a model call. Approach C's rationale rests on 'no model tool-use during generation' and avoiding the model's own subjective read of prose; if the quoted-line extraction is itself done by an LLM interpreting search-result text, the pipeline still ends in model interpretation, just relocated to a pre-fetch stage instead of removed. Open Questions still lists whether the source 'delivers an external signal, or just more text to interpret' as unresolved — this is the same original obligation (round 1's R1-6) still unmet, since the mechanism added this round doesn't settle it.

**Remedy**

> Specify how the 'quoted line' is extracted from search results — deterministic string/frequency matching, or a separate model call — and if a model call, state why that still counts as an external signal rather than model interpretation relocated one stage earlier.

### R2-2 — feasibility

**Problem**

> No reconciliation step is defined between the externally-fetched 'quoted line' (from a web search result, possibly a different lyrics site with different punctuation, spacing, or simplified/traditional character variants) and the actual lrclib.net-sourced lyrics text that resolveLyricsBatch uses to build the question. Blanking requires the grounding phrase to exist as an exact or reliably matchable substring of the synced lyrics passed to the model; if the two sources diverge textually, the pre-fetch signal can't be mechanically applied to the real lyrics text used for the blank.

**Remedy**

> Define how the fetched quoted line is matched/aligned against the lrclib.net lyrics text (exact substring match, fuzzy match, or model-assisted alignment), and what happens when no reliable match is found — presumably the same fallback-to-today's-method path, but state it explicitly.

### R2-3 — consistency

**Problem**

> Approach C's Risk rating was revised this round to 'provisional, not yet substantiated' because the fetch mechanism isn't chosen, but the Effort rating ('Effort M') was left unqualified and unchanged, even though effort could vary substantially depending on which mechanism the spike confirms (a simple per-song API call vs. a web-search-and-parse pipeline with result matching, per R2-2). The same mechanism uncertainty that invalidated the Risk rating applies equally to Effort, but only Risk was hedged.

**Remedy**

> Either qualify Effort M as provisional pending the mechanism decision, consistent with how Risk was hedged, or state why Effort is expected to hold regardless of which mechanism the spike confirms.

### R2-4 — clarity

**Problem**

> Premise 5 references 'constraint #2' ('worth minimizing surface area given constraint #2'), but the Constraints section lists three unordered bullets with no numbering, so the reference is ambiguous to a reader — it appears to mean the 'hobby project, no monetization' bullet, but this must be inferred rather than confirmed.

**Remedy**
