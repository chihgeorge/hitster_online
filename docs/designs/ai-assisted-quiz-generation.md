## Problem Statement

Make the host's life easier when creating and editing a quiz (playlist), using AI to help. Today a host pastes a YouTube playlist URL, an existing server-side step (`lib/ai-metadata.ts`, Claude Haiku) auto-resolves title/artist/year per track, and the host reviews/corrects results in a flat editable table (`PlaylistEditor.tsx`). When the AI got something wrong, or the host wants to build a themed quiz from an idea rather than a pre-existing playlist, there's no way to do that in-app — the host's actual workaround today is to paste the table into ChatGPT/Claude's own web chat, describe what to fix or generate, and copy the result back in by hand.

## What Makes This Cool

A dedicated "✨ Generate quiz" flow: the host describes a theme (a decade, genre, artist, vibe — or a partial list of songs they already have in mind) and gets back a complete, ready-to-play quiz — songs, resolved metadata, and (for Lyrics Mode) the fill-in-the-blank questions — in one shot, reviewed before the room even exists. No YouTube playlist hunting required at all. This is the "whoa" moment closest to the host's original instinct: a full playable round from one sentence.

## Constraints

- Song additions need a *real, playable* YouTube videoId, not just an AI-guessed title/artist. `lib/ai-metadata.ts`'s Claude Haiku call can resolve metadata for a *given* video reliably, but it cannot itself produce a valid videoId for "a song like X" — that requires an actual YouTube search.
- `lib/youtube.ts` (YouTube Data API v3 client) currently only wraps `playlistItems` and `videos` — there is no `search.list` integration yet. This is new server-side surface, not a reuse of existing code.
- Any AI-proposed change (edit or add) must be shown to the host as a reviewable diff before it lands in room state — never a silent overwrite. This matches the existing `PlaylistEditor.tsx` dirty-row pattern (`isDirty`/`getDraft`), which is already structurally a diff-review UI.
- Lyrics Mode question generation (lyric context + blank sentence) already exists via lrclib.net + AI (used today when starting a Lyrics Mode game) and should be reused, not rebuilt, for AI-generated quizzes.
- This is a fan/hobby project — no monetization pressure, no external users to onboard. The bar is "does this make game night prep more fun," not growth or retention metrics.

## Premises

1. The host optionally starts with SOME content — a few song names, a theme, an incomplete list, or a full YouTube playlist URL, not necessarily a complete curated playlist — and AI's job is to complete/enhance the set: fill gaps, suggest more songs, resolve metadata, generate Lyrics Mode fill-in-the-blank questions. Not just "correct an already-resolved table." *(Revised during the session — the first draft framed this too narrowly as "fix wrong metadata"; the host corrected it to include completing an incomplete set.)*
2. Wherever possible, build on existing infrastructure rather than inventing new architecture — except where a real capability gap (YouTube search) requires new surface. This means different reuse targets depending on approach: Approach C (chosen) feeds a generated song set into the room-creation path that already accepts a resolved `songs: EditableSong[]` array directly (`START_GAME`'s existing optional `songs` field, `lib/game.ts:106` — no room needs to exist yet for this, unlike `UPDATE_SONG`). The `UPDATE_SONG` party action and `PlaylistEditor`'s dirty-row diff state remain the reuse target for a *later*, separate in-place-editing capability (Approaches A/B, not built in this iteration — see Open Questions).
3. Any AI edit or addition must show a reviewable diff before applying — never silently overwrite table or room state from a chat/generation instruction.

## Approaches Considered

### Approach A: Chat-to-diff editor (minimal viable — CHOSEN, see Recommended Approach)
Chat box above `PlaylistEditor` fixes existing rows only, via a new `proposeEdits()` in `ai-metadata.ts` reusing the existing fetch/batch pattern. Diff rendered through the table's existing dirty-row styling; applied through the existing `setField`/`handleSaveAll`/`UPDATE_SONG` path. No song addition, no new external API. Effort S (a weekend), risk Low. Rejected — doesn't cover the "AI completes/suggests new songs" half of the premise; the host wanted the fuller capability.

### Approach B: Chat quiz co-creator (ideal architecture — not chosen)
One chat thread handles both fixing AND adding songs, in-place on the existing editor. Adding a song = Haiku suggests title/artist → new `searchVideo()` in `lib/youtube.ts` resolves it to a real videoId → merged into the same diff-review UI as edits, showing a thumbnail so the host can catch a wrong match. Effort M (a few evenings), risk Medium (search-match accuracy). Rejected in favor of the standalone-generator framing, though its `searchVideo()` addition and reviewable-diff UI are directly reused by Approach C below.

### Approach C: Standalone quiz generator (originally chosen by the host — deferred during eng review, see Recommended Approach)
A dedicated "✨ Generate quiz" screen, separate from (but complementary to) the existing playlist-URL import flow. The host describes a theme or a partial list of songs; AI proposes a complete song set (title/artist/year via Haiku, resolved to real videoIds via the new `searchVideo()` YouTube search step); for Lyrics Mode, the existing lrclib.net + AI lyric-context pipeline generates the fill-in-the-blank questions for the chosen songs in the same pass. The full proposed quiz — songs, years, and (if applicable) lyric questions — is shown as a reviewable set before the room is created, using the same diff/review conventions as the existing `PlaylistEditor`. The approved set is then passed as `songs: EditableSong[]` into the existing `START_GAME` party action — the same field the current manual-edit-override path already uses — so room creation itself needs no new mechanism.
Effort: M (a few evenings — a new YouTube search integration plus a new review screen, but the room-creation hookup is a pre-existing field, not new plumbing). Risk: Medium (search-match accuracy is the main failure surface; see Open Questions).

## Recommended Approach

**Reopened during /plan-eng-review's mandatory Outside Voice pass — see Decision ledger below.** Approach C (standalone generator) was the host's original pick, but an independent Claude-subagent challenge (Codex `model_unusable` this session) surfaced load-bearing gaps: the "reviewable diff" UI for a from-scratch generated set does not actually exist yet (`PlaylistEditor.tsx` has no diff concept beyond its dirty-row table, which only works for editing rows already in the table); the existing playlist-import path runs every resolved videoId through `fetchEmbeddableVideoIds()` (`party/index.ts:556`) before accepting it and `searchVideo()`'s plan never mentioned this; and the YouTube Data API quota math (100 units/`search.list` call × up to 20 songs = ~2,000 units against a 10,000/day default budget shared with the existing import flow) caps the feature at ~5 generations/day before it also breaks the existing playlist-URL import — a go/no-go constraint the original plan filed as a minor open question. Most fundamentally: the actual observed pain point (pasting the existing table into a chat model to fix it) is a metadata-editing problem, and Approach C was building a bigger, riskier, unvalidated song-generation capability to solve it.

**Revised recommendation: build Approach A first.** Chat-to-diff editor on the existing playlist table — no song addition, no YouTube search, no quota exposure, no new review screen. Reuses `PlaylistEditor.tsx`'s existing dirty-row diff state directly (the very thing Approach C would have had to build from scratch). Ships in a weekend, directly matches the workaround already observed, and validates whether song-addition (Approach B/C's territory) is actually wanted before spending a quota-constrained, undesigned effort on it. Approach C is deferred, not cancelled — pursue it only once Approach A ships and hosts actually ask for "generate songs from a theme," not before.

## Open Questions

- **Song-match confidence UI:** how does the host visually confirm the YouTube search matched the *right* version of a song (not a cover, remix, or wrong artist)? Approach B's cross-model note flagged this — needs a thumbnail + title shown per suggestion, not just text, before the host accepts.
- **Failure mode when AI suggests an unfindable song:** what happens when `searchVideo()` returns nothing or a clearly bad match for an AI-suggested title/artist? Silently drop it, flag it for the host to resolve manually, or retry with a broader query?
- **Duplicate songs:** if an AI-suggested or search-resolved song duplicates one the host already listed (in a partial seed list) or one already present when extending a playlist, is it silently deduped, flagged to the host during review, or left for the host to notice and remove themselves? Given Premise 3 (reviewable diff, never silent), flagging rather than silent dedup is the likely default — not yet decided.
- **Where does this live relative to the existing playlist-URL flow?** A new screen, a tab on the existing host setup panel, or a "or generate one instead" link next to the URL input? Not decided in this session.
- **Game-mode selection timing:** Timeline vs. Lyrics Mode changes what the generation pipeline must produce (Lyrics Mode needs the extra lyric-question step). Is mode chosen before entering "Generate quiz," as the first step within it, or does the screen generate mode-agnostically and branch afterward? Not decided in this session — needed before Next Step 2/4 can be scoped precisely.
- **Batch UX and quota-aware caps:** a themed request for "20 songs" chains roughly 1 Haiku call + up to 20 `search.list` calls + (Lyrics Mode) up to 20 lrclib+AI lyric calls from one host action. Two distinct cost dimensions, both uncapped in this design: (a) **latency/UX** — do results stream in progressively as each song resolves, or does the host wait synchronously for the whole batch, and what happens on partial failure mid-batch; (b) **YouTube Data API quota** — `search.list` costs ~100 quota units per call versus the cheap `playlistItems`/`videos` calls already in use (a default 10,000-unit daily budget), so a single 20-song generation could burn ~2,000 units and, if it shares an API key with the existing playlist-URL import flow, degrade or break that flow too. Both need a request-size cap and (for quota) possibly a separate API key or a per-day generation limit — not decided in this session.

## Success Criteria

**(Revised — see Recommended Approach.)** A host who already has a YouTube playlist loaded can describe a fix in plain language ("the 3rd song's year is wrong, it's 1998") instead of clicking into table cells, sees the AI's proposed change rendered as a dirty row exactly like a manual edit would look, and applies or discards it through the same Save/Apply flow that already exists. Generating a whole new quiz from a theme, with no starting playlist, is explicitly deferred (Approach C) — not a success criterion for this iteration.

## Next Steps

**(Revised for Approach A — Approach C's steps are preserved below under "Deferred: Approach C implementation" for when it's picked back up.)**

1. Add `proposeEdits(instruction: string, songs: EditableSong[], apiKey)` to `lib/ai-metadata.ts`, reusing its existing fetch/batching pattern with a new system prompt: given the current song list and a natural-language instruction, return a diff array `[{videoId, field, oldValue, newValue}]`. On whole-call failure (network/API error), mirror `resolveBatch`'s existing graceful-degradation pattern — log, return empty, surface a "couldn't process that, try again" state rather than a silent blank result.

3. Add a new party message type `PROPOSE_EDITS` (client→server) / a corresponding server reply, handled in `party/index.ts` alongside the existing `LOAD_PLAYLIST` and `UPDATE_SONG` handlers — same transport pattern, same server-side API-key handling.
4. Add a chat input box above `PlaylistEditor`'s table. On submit, call the new party action; render the returned diff using the table's *existing* dirty-row styling (`isDirty`/`getDraft`) — no new diff UI component needed, this is the whole point of choosing A.
5. Wire "Apply"/"Discard" through the existing `setField`/`handleSaveAll`/`UPDATE_SONG` path, unchanged.
