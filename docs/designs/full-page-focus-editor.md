## Problem Statement

The existing AI chat-to-diff editing (v0.9.0.0/v0.11.0.0) works over a flat table inside a live room — `PlaylistEditor.tsx` for timeline-mode songs, a separate inline table in `app/room/[code]/host/page.tsx` for Lyrics-mode rounds. **Verified by `/plan-eng-review` (2026-09-22):** this AI editing does NOT currently work on the room-less `/playlists` page — `app/playlists/page.tsx` never passes `onProposeEdits` to `PlaylistEditor`, so its "✨ Ask AI" box doesn't render there at all (confirmed via `grep`; `PlaylistEditor.tsx:251` gates the whole box on that prop being present). Wiring AI editing onto `/playlists` is exactly T8, still unbuilt — this design's Next Steps #4 includes building it, not just porting an existing capability. The host wants a different editing *feel* on top of whichever surface: a full-page view showing one question at a time (the image/text centered, answer options at the bottom if any), where they can edit anything — text, image, video, or the room's game type — by typing a command, "like talking to Claude." Direct quote: "Host can edit anything on the page using AI by typing command, like I talk to you."

This redesign was explicitly deferred as T8 of the just-shipped quiz-bank decoupling arc (`docs/designs/decouple-quiz-bank.md`) — building the standalone-page AI-editing equivalent before this redesign landed risked building it twice.

## What Makes This Cool

Conversational control over game content, not the layout change itself. Per the session's own second-opinion cold read: the tell is "like I talk to you" plus the impulse to make the AI-editable surface as broad as possible (image, text, video, game type) before scope-locking walked it back — the host is excited by *talking to the content*, and the one-item-at-a-time screen is what makes that feel focused and conversational instead of like editing a spreadsheet.

## Constraints

- The two existing data shapes stay as-is: timeline songs (`EditableSong`: videoId/title/artist/year) and lyric rounds (`LyricsRound`: videoId/title/artist/language/lyricContext/blankSentence/acceptableVariants). No new question kinds, no new template system (ruled out explicitly — see Premises).
- Real YouTube search ("change the video" via AI) stays deferred, same as the prior design doc — same unresolved quota risk. Derivation (carried over from the superseded doc, `georgechih-main-design-20260922-165858.md`): `search.list` costs ~100 YouTube Data API units/call vs ~5 for the metadata calls already in use; a single 20-song batch (~20 `search.list` calls) burns ~2,000 units against a shared 10,000-unit/day default budget — capping the feature at **~5 full twenty-song batches/day**, not 5 individual searches, before it also degrades the existing playlist-URL import flow that shares the same key. Same song-match-confidence risk as before.
- The AI chat-to-diff engine itself (`lib/ai-metadata.ts`'s `proposeEdits`/`proposeLyricEdits`) is reused as-is — no changes to how AI proposes edits, only to how the host views and applies them.
- Lyrics-mode data during an active room comes from three different sources depending on game phase — `lyricsState.rounds` (locked deck), `lyricsPreview` (Haiku preview stream), `lyricOverrides` (host's manual edits) — merged per-row in `host/page.tsx`'s existing table render. Any Lyrics-mode single-item view has to reproduce this correctly, live, inside the room's WebSocket lifecycle.
- Fan/hobby project — no monetization pressure, no external users, the bar is "does this make game night prep more fun."

## Premises

1. Pure navigation/layout redesign over the EXISTING two data models — no new question kinds (multiple-choice, image-based, etc.), no new template system. — **agreed**
2. Real YouTube search stays deferred. — **agreed**
3. ~~The new one-item-at-a-time page REPLACES both existing table views entirely~~ — **revised.** The second-opinion pass challenged this directly: the host never actually asked to lose the table, and full replacement triples the scope (loses the table's bulk-review/bulk-save, and forces reproducing Lyrics mode's 3-way phase-merge inside a new component with no existing list screen to build from). **Revised premise:** the single-item view COEXISTS with both existing tables as an additive "Focus" mode — the table keeps doing bulk scan/bulk-save, Focus mode gives the one-item, talk-to-AI experience.
4. "Ask AI for suggestions" = a per-item "check this one" action on the currently-viewed item, using the same diff-review pattern already established — not a whole-playlist scan. — **agreed**

The Lyrics table's 3-way phase-merge is real, live-room-socket complexity that a straight "re-skin as single-item" glosses over.

## Approaches Considered

### Approach A: Minimal Focus Mode — timeline only (not chosen)
New `components/SongItemEditor.tsx` on `/playlists` only, `PlaylistEditor.tsx`'s table untouched. Effort S (a weekend), risk Low. Matches the cross-model second opinion's own build plan file-for-file. Rejected — host wanted full parity across both modes in this round, not a staged rollout.

### Approach B: Focus Mode for both modes, shared hook architecture (CHOSEN — see Recommended Approach)
Same as A, plus a Lyrics-mode single-item view inside the room's live `host/page.tsx`, built on a shared `lib/use-item-draft.ts` hook covering both data shapes. Effort L (over a week), **risk Low-Medium** — revised by `/plan-eng-review` (2026-09-22) after tracing the actual code: `party/index.ts:1141-1143` sets `lyricsState.phase = "preview"` and `lyricsState.rounds = this.lyricsDeck` in the SAME assignment, atomically, when `START_LYRICS_GAME` completes. The client's lyrics table goes read-only the instant `rounds.length > 0` — simultaneous with `phase` becoming `"preview"`, not after it. So the real editable window is only `lyricsState === null` (before the host has ever clicked "Start Lyrics"), where `lyricOverrides` (`host/page.tsx:59`) is plain `useState`, never touching the server until it's bundled once into the `START_LYRICS_GAME` payload — the same shape and risk profile as `PlaylistEditor`'s own `editing: Record<videoId, Partial<EditableSong>>`. There is no persisted server-side round data being live-edited at any point; the original "live-room-state surgery, could corrupt an in-progress game" framing was based on an incorrect model of the code, not the actual mechanism.

### Approach C: Ship the proactive-check idea first, no navigation change (not chosen)
The cross-model second opinion's "coolest version" shipped directly on the existing tables — a "✨" per-row check icon calling `proposeEdits`/`proposeLyricEdits` with a fixed review instruction. Effort XS (a day or two), risk Low, zero new components. Rejected — doesn't deliver the full-page one-item experience the host actually described; a hypothesis test, not the redesign itself.

## Recommended Approach

**B, per the host's explicit choice** (chosen over the S/Low-risk recommendation, Approach A) — full parity across timeline and Lyrics modes in this round.

**Revised by `/plan-eng-review` (2026-09-22):** the tradeoff as originally framed — accepting real live-room-data risk in exchange for full parity — turned out not to be the actual tradeoff. Tracing the code showed Lyrics-mode editing is local-only client state, structurally identical to the timeline mode's own already-proven pattern (`PlaylistEditor`'s `editing` map), never touching persisted server state before one Save. Approach B is now Low-Medium risk, not High — the earlier choice of B over A was correct, but for a smaller reason than originally stated (complexity/effort, not risk avoidance-vs-acceptance). The one piece of genuine care Approach B still needs: reproducing the table's exact editable-window condition correctly (see Success Criteria's corrected gating below) — getting that condition wrong would show Focus mode as editable when it shouldn't be, or vice versa, which is a real (if much smaller than originally feared) correctness risk.

## Open Questions

- ~~**Shared hook shape**~~ — **Resolved by `/plan-eng-review` (2026-09-23).** Verified `PlaylistEditor.tsx`'s `editing: Record<videoId, Partial<EditableSong>>` + `setField`/`getDraft`/`isDirty` and `host/page.tsx`'s `lyricOverrides: Record<videoId, Partial<{lyricContext, blankSentence}>>` are structurally identical draft-tracking shapes — the only real difference is persistence (timeline: `PUT /parties/playlist/:id`'s `UPDATE_SONG` action per song; lyrics: bundled once into the `START_LYRICS_GAME` payload). `lib/use-item-draft.ts` stays narrow — owns only draft state (`getDraft`/`setField`/`isDirty`/`discard`/`discardAll`/`dirtyCount`), generic over the item shape. Persistence (Save/handleSaveSong/handleSaveAll-equivalents) stays in each caller, unchanged from today. Signature:
  ```ts
  function useItemDraft<TBase extends { videoId: string }, TFields extends Partial<TBase>>(
    items: TBase[]
  ): {
    getDraft(item: TBase): TBase;
    setField<K extends keyof TFields>(videoId: string, field: K, value: TFields[K]): void;
    isDirty(item: TBase): boolean;
    discard(videoId: string): void;
    discardAll(): void;
    dirtyCount: number;
  };
  ```

Between the host clicking "Start Lyrics" and the server's `lyricsState` broadcast arriving (network round-trip — this app's real use case is a party on venue wifi, not a fast connection), the client still reads `lyricsState === null` and Focus mode would incorrectly stay editable. **Fix required, not optional** — see Next Steps.

## Success Criteria

- A host can open a single song (timeline mode) or a single lyric round (Lyrics mode) full-screen, see its content centered, and type an AI edit command that applies through the same reviewable-diff flow the table already uses.
- The host can move between items (prev/next) within Focus mode without leaving it — in scope for this round regardless of whether URL deep-linking is resolved (see Open Questions). Boundary behavior: prev is disabled on the first item, next is disabled on the last — no wraparound (matches the exact, small, fixed-length lists this editor works over; a host expecting "next" to loop back to song 1 would more likely read that as a bug than a feature).
- The existing table view keeps working exactly as it does today — Focus mode is additive, not a replacement, and ships with zero regression to `PlaylistEditor.tsx` or `host/page.tsx`'s existing table.
- Lyrics-mode Focus view correctly reflects `lyricsPreview` + `lyricOverrides` merged the same way the existing table does, gated by `lyricsState === null` AND a new local pending flag (see Next Steps) that closes the `START_LYRICS_GAME` round-trip race — verified by tracing the existing table's merge logic before building the new view, not assumed.
- **Lyrics Focus mode must actually import and consume `useItemDraft`, not reimplement its own copy of the draft-tracking logic** — added by `/plan-eng-review` (2026-09-23) after the outside-voice pass flagged that Next Steps' original wording ("benefits from a proven pattern") didn't actually require this. Without this criterion, the plan could ship timeline-only (the reason Approach A was rejected in the first place) without that ever being a deliberate decision.
- **Not in this round:** "game type via AI" (switching the room's mode by chat command) and real YouTube video search/replacement both stay deferred — approving this document does not commit to either.
- **Resolved by `/plan-eng-review` (2026-09-22):** when the underlying list has zero items, Focus mode's entry point simply doesn't render — matches existing precedent exactly (`PlaylistEditor`'s table already guards on `readySongs.length > 0` before rendering anything, `host/page.tsx:628,635`). No empty-state screen to build.
- **Corrected by `/plan-eng-review` (2026-09-22 — was wrong in the original doc):** Focus-mode editing on the Lyrics side is only enabled while `lyricsState === null` — i.e., before the host has ever sent `START_LYRICS_GAME`. `party/index.ts:1141-1143` sets `lyricsState.phase = "preview"` and `lyricsState.rounds = this.lyricsDeck` in the same assignment, atomically — the moment `lyricsState` exists at all, `rounds` is already populated and the table (and Focus mode) must go read-only, NOT stay editable through a "preview sub-phase" as originally stated. The correct gate is `!lyricsState`, not `lyricsState?.phase === "preview"`.
