# Design: Guess Mode — guess the song name/artist

## Problem Statement
hitster_online has two game modes: Timeline (guess the release year, turn-based
placement) and Lyrics (AI blanks part of a song's chorus, everyone answers
simultaneously against a timer). Neither mode tests the most basic music-trivia
skill: recognizing the song itself. The user wants a third mode where the audio
plays and players guess the song name and/or artist.

## What Makes This Cool
Unlike Lyrics mode, this needs **zero AI generation** — every song's title and
artist are already known the moment a playlist loads. That's a real "whoa": the
cheapest mode to build is also the most classic "name that tune" experience.
The user's own scoring design — independent points for title, independent
points for artist, plus a bonus for nailing both — makes partial recognition
feel rewarding instead of binary pass/fail, which is a genuinely richer
scoring model than either existing mode has.

## Constraints
- Solo hobby project, no monetization, played with a regular game-night group.
- Existing `GameMode` union (`"timeline" | "lyrics"`) and PartyKit Durable
  Object room model (`party/index.ts`, already 1382 lines) must be extended,
  not replaced.
- Lyrics mode is shipped and actively played — any refactor touching its code
  path carries real regression risk on a feature people use tonight.

## Premises
1. **Agreed.** No AI generation needed — title/artist are already in the
   loaded playlist, unlike Lyrics mode which needs AI to pick a blank. Strictly
   simpler and cheaper to build than Lyrics mode was.
2. **Agreed.** Reuses Lyrics mode's whole shape: simultaneous timed rounds, a
   mode-specific game state object, host-config (timer/rounds), the same
   broadcast/reveal/next-round flow — just a different round payload and a
   2-field scored answer instead of 1.
3. **Agreed.** Scoring per round = title points (if title guess matches) +
   artist points (if artist guess matches) + a bonus if both match, each
   still scaled by answer speed like Lyrics mode's `computePoints`. Exact
   formula (R1-2): `total = speedScale(titlePts) + speedScale(artistPts) +
   speedScale(bonusPts)`, where `speedScale` is `computePoints` applied with
   ONE timestamp — the single moment the player submits both fields together
   (not two separate per-field timestamps, since both fields are one submit
   action).
4. **Agreed.** This is a THIRD sibling mode (`GameMode` gains a 3rd value),
   not a variant flag on Lyrics mode — it has its own state shape (two answer
   fields, not one) and needs its own UI screens.

## Scoring & Grading Rules
- **Missing/blank field (R1-3):** a player who leaves the title or artist
  field empty at submit time is graded as incorrect for that field only —
  0 points, not bonus-eligible. The other filled field is still graded
  normally. **A true timeout — no submission received at all before the
  deadline (R2-2)** — is treated identically to an all-fields-blank
  submission: both fields score 0, no bonus, same as Lyrics mode already
  treats a non-answer as simply absent from `ls.answers` at scoring time.
- **Track with no artist metadata (R1-5):** some playlist imports carry an
  empty artist string. A round on such a track scores title-only for
  everyone — the artist field is hidden/disabled for that round rather than
  silently ungradable, so players aren't penalized for a data gap. Guess
  mode's `toPublicView` (Approach B) carries an explicit `hasArtist: boolean`
  flag during `guessing` — not inferred from an empty string client-side —
  so the client knows to hide the artist input for this specific round
  before any answer data would otherwise reveal it (this eng review's
  finding 4).
- **`isCorrect` as v1 baseline (R1-1):** `lib/fuzzy.ts`'s existing
  `isCorrect` is the accepted grading function for BOTH fields in v1,
  called once against the title and once against the artist. Open Question
  3's normalizer refinement (multi-artist strings, "feat." noise,
  romanization) is an explicit v1.1 follow-up once real playtesting surfaces
  which edge cases actually matter — Next Steps step 3 is not blocked on it.
- **Point-value location (R1-6):** point values (title/artist/both-bonus)
  are static exported constants in code for v1, not a host-configurable
  field — matching Lyrics mode's `computePoints` scaling constant, which is
  also code-level, not host-config. Making them host-tunable (like
  timer/rounds) is a possible v1.1 enhancement once defaults are validated
  by playtesting (Open Question 2).

## Approaches Considered
### Approach A: Copy Lyrics mode's state machine
Duplicate `LyricsGameState`/config shape and `party/index.ts`'s Lyrics
handlers (start/submit/results/next) into a parallel `GuessGameState` and its
own handler set, adapted for the two-field compound scorer.
- Effort: M. Risk: Low.
- Pros: fastest to ship; zero risk to Lyrics mode's currently-shipped code.
- Cons: ~250-300 lines of structurally-near-identical round-lifecycle code
  added to an already-1382-line `party/index.ts`; the next mode after this
  one triples the duplication.

### Approach B: Extract a shared timed-round engine
Pull the "simultaneous timed round: start→submit→reveal→next" state machine
out of Lyrics mode into a shared generic engine (round data + a
mode-specific scoring hook), then have both Lyrics mode AND the new Guess
mode plug into it.
- Effort: L. Risk: Medium (touches Lyrics mode's shipped code).
- Pros: the second real user of this pattern is exactly when extracting it
  stops being premature (reuse ladder rung 1); avoids ~250-300 lines of
  duplication; every future simultaneous-round mode benefits.
- Cons: bigger diff; real regression risk on a feature people play tonight —
  needs careful test coverage and a scrutinized spec review before landing.
- **Engine contract sketch (R1-7):** the shared engine owns phase transitions
  (loading→preview→playing→guessing→results→ended), the timer, and the
  broadcast/reveal/next-round flow. It does NOT know what an "answer" or a
  "round" contains — each mode's round is an opaque payload, and each mode
  supplies its own `scoreAnswers(round, answers, config) →
  Record<playerId, unknown>` callback (R3-1: widened from the original
  `{correct, points}` — that shape only fit Lyrics mode's single
  correct/incorrect result and couldn't hold Guess mode's per-field
  correctness + 3-way point breakdown; the result is now mode-opaque, typed
  at each mode's call site, same as `round`/`answers` already are), invoked
  at the results transition. Lyrics mode's existing `isCorrect`/
  `computePoints` call becomes its `scoreAnswers`; Guess mode's compound
  scorer (Scoring & Grading Rules, above) becomes its own. This keeps
  mode-specific typing out of the shared engine — the engine's own
  state/types stay generic (`round: unknown`, `answers: Record<playerId,
  unknown>`), typed at each mode's call site instead.
  **Answer secrecy across phases (R2-1):** the engine never broadcasts the
  full private `round` object directly. Each mode also supplies a
  `toPublicView(round, phase) → unknown` function; the engine broadcasts
  ONLY that function's output, called fresh on every broadcast with the
  current phase. This is not a new pattern — it's exactly what Lyrics mode
  already does today (`PublicLyricsRound` strips `blankSentence` during
  `guessing`, reveals it at `results`); the extraction just promotes that
  per-mode redaction into an explicit part of the shared engine's contract
  instead of leaving it implicit in Lyrics-mode-specific broadcast code.
  Guess mode's `toPublicView` strips `title`/`artist` during `guessing`
  the same way. The private `round` (with the real answer) stays
  server-side only, passed to `scoreAnswers` at the results transition —
  never broadcast.
  **Reveal delivery (R3-2):** the engine also calls a mode-supplied
  `toPublicResults(round, answers, scores) → unknown` at the results
  transition, and broadcasts ITS output alongside the results-phase
  `toPublicView` — this is the missing piece that actually gets submitted
  guesses and `scoreAnswers`' output to clients for the reveal screen (the
  contract previously only specified broadcasting the redacted round,
  never the answers or scores). For Lyrics mode this returns the existing
  reveal shape (correct/incorrect + points); for Guess mode it returns the
  per-player title/artist guesses, per-field correctness, and 3-way point
  breakdown that Success Criteria requires.
  **Answer-leak fix (this eng review's P1):** `broadcastLyricsState()` as
  shipped today sends every player's RAW answer text to every client during
  `guessing` (`sanitizedLyricsState` spreads `...ls` unredacted, and
  `handleSubmitLyricsAnswer` broadcasts immediately after storing it) — a
  player who submits last can read everyone else's guesses off the wire
  before answering. The extraction fixes this for both modes: during
  `guessing`, the engine broadcasts only a redacted per-player
  `hasAnswered: boolean` map, never raw answer text; the real `answers`
  object stays server-side until `toPublicResults` reveals it.
  **Client blast radius (this eng review's D-eng-4):** genericization stays
  INTERNAL to `party/index.ts`. `LyricsGameState`/`PublicLyricsGameState`
  (and the new `GuessGameState`/`PublicGuessGameState`) stay concrete,
  mode-specific facade types on the wire and in every client file — the 4+
  files that consume them directly today (`app/room/[code]/host/page.tsx`,
  `app/room/[code]/play/page.tsx`, `app/room/[code]/screen/page.tsx`,
  `components/LyricsTable.tsx`, plus their test files) are completely
  unaffected by the extraction; none of them see `unknown` types or need
  re-narrowing.
  **Shared function signatures (this eng review's D-eng-2):** the "reuse
  `isCorrect`/`computePoints` as-is" premise (R1-1, Premise 3) doesn't hold
  against the actual code — `computePoints(roundStart, answerTs,
  timerSeconds)` has no points parameter (hardcoded 500-point ceiling), and
  `isCorrect(playerAnswer, round: LyricsRound, config)` is typed against
  `LyricsRound` specifically, reading `round.blankSentence`/
  `round.acceptableVariants` off that concrete type — it cannot take a
  title or artist string directly. Both need signature widening BEFORE
  Guess mode can actually call them: `computePoints` gains a `maxPoints =
  500` parameter (existing Lyrics-mode callers pass 500 explicitly,
  preserving today's behavior byte-for-byte); `isCorrect` takes a target
  string + `acceptableVariants` array directly instead of a `LyricsRound`
  object (Lyrics mode's call site passes `round.blankSentence`/
  `round.acceptableVariants` explicitly instead of the whole round). Both
  are additive/signature-only changes with no behavior change for existing
  callers — `lib/fuzzy.test.ts`'s fixed-value assertions must be
  re-verified to still pass unchanged, not just "should."
  **Sequencing risk (this eng review, informational):** the engine contract
  above was designed against Lyrics mode as the only consumer; expect it to
  need small revision once Guess mode's actual two-field/compound-result
  shape is attached in Next Steps step 2/3 (this is exactly how R3-1 was
  found — a contract that looked complete with one consumer didn't fit the
  second). Next Steps step 1's "full existing Lyrics test suite must stay
  green" gate is necessary but not sufficient proof the contract is final;
  budget for a second, smaller green-suite check after step 2/3 attaches
  Guess mode, not just at step 1.

### Approach C: Buzz-in variant instead of independent timers
Same state shape as A, but first correct answer locks the round for
everyone and wins a big bonus, instead of every player scoring
independently by their own speed.
- Effort: M. Risk: Low.
- Pros: distinct, more "quiz show" game feel; genuinely different from
  Lyrics mode's flat simultaneous-answer format.
- Cons: real fairness tradeoff (a correct-but-not-fastest player scores
  zero, even a slow typist who knew the answer); doesn't compose cleanly
  with the compound title+artist+bonus scoring already decided — partial
  credit and lock-on-first are an awkward combination.

## Recommended Approach
**B — extract a shared timed-round engine.** The user chose this explicitly,
accepting the higher effort/risk for the long-term payoff: Lyrics mode and
Guess mode both being simultaneous-timed-round games isn't a coincidence,
it's a real recurring shape in this codebase, and duplicating a 250+ line
state machine a second time is exactly the kind of slop the reuse ladder
exists to prevent. Given the regression risk on shipped Lyrics-mode code,
the spec-review loop below is scoped to scrutinize that risk specifically
(test coverage on the extraction, not just the new mode) before this lands.

## Open Questions
1. **Clue-tax mechanic (deferred, not designed here):** the subagent's
   partial-reveal-under-timer idea is a strong v1.1 candidate but needs its
   own design pass (what gets revealed, how points shrink, host toggle or
   always-on) — explicitly out of scope for this doc.
2. **Point values:** exact title-points / artist-points / both-bonus
   constants aren't fixed yet — pick sensible defaults (e.g. title 250,
   artist 250, both-bonus 100, all still speed-scaled via `computePoints`)
   and make them easy to tune, not hardcoded magic numbers buried in logic.
3. **Artist fuzzy-matching edge cases:** multi-artist strings ("A feat. B"),
   romanization variants, and band-name punctuation need a look before
   `isCorrect` is trusted as-is for the artist field — may need its own
   normalizer or an `acceptableVariants`-style artist alias list.

## Success Criteria
- A host can start a Guess Mode round from a loaded playlist with zero AI
  calls in the critical path.
- Players submit a title guess and an artist guess; each is graded
  independently with fuzzy matching, and a correct-both bonus applies.
- The results/reveal screen (R1-4) shows, per player: their submitted title
  and artist guesses, which of the two (if either) was correct, and the
  point breakdown (title pts / artist pts / bonus) that produced their
  round total — not just a single pass/fail like Lyrics mode's reveal. For
  a title-only round (R1-5's no-artist-metadata case), the artist
  row/column is omitted from the reveal screen entirely, consistent with it
  being hidden/disabled at submit time (R2-3) — never shown as a blank or
  "N/A" artist guess, since no player was ever asked for one.
- Lyrics mode's existing test suite and e2e specs still pass unmodified
  after the shared-engine extraction, INCLUDING explicit coverage of the
  `handleStartLyricsGame` re-entrancy guard (R1-8, v0.13.4.0) — a general
  "tests stay green" bar only catches a regression there if that specific
  scenario has its own test, which it does
  (`party/index.test.ts`'s "rejects a second START_LYRICS_GAME..." test);
  confirm that test's assertions still exercise the guard's actual location
  post-extraction, not just that it still passes.
- Playable end-to-end with the regular game-night group before any clue-tax
  work starts.

## What I noticed about how you think
- You specified the scoring formula — "title points, artist points, and if
  both correct extra points" — before anything about UI or flow. That's the
  real idea here: a richer, partial-credit scoring model, not just a new way
  to answer a question.
- When offered the cheaper, lower-risk approach (copy Lyrics mode's code) vs.
  the one that actually fixes a structural problem (extract a shared
  engine), you picked the harder one on purpose. That's not impatience —
  that's caring about what the codebase looks like in six months, not just
  whether this feature ships Friday.
- You explicitly deferred the flashiest idea from the second opinion (the
  clue-tax mechanic) rather than scope-creeping v1 to include it. Shipping
  the boring complete thing first, saving the exciting risky thing for
  after it's proven — that's a real product instinct, not just discipline.

## Reviewer Concerns

Disposition: CONCERNS_RECORDED

Stop: MAX_ITERATIONS

### R3-1 — feasibility

**Problem**

> The 'Answer secrecy across phases (R2-1)' fix concretely types scoreAnswers' return as Record<playerId, {correct, points}> — a single boolean and a single number per player. Success Criteria requires the reveal screen to show, per player, per-field correctness (title correct? artist correct?) and a point breakdown of THREE separate values (title pts / artist pts / bonus pts). A single {correct, points} pair cannot carry that — it can express at most one correctness flag and one total. This also contradicts the same paragraph's claim that 'the engine's own state/types stay generic ... typed at each mode's call site instead': the round/answers types are left as unknown, but the scoreAnswers RESULT type is not generic at all — it's concretely fixed to a shape that only fits Lyrics mode's single correct/incorrect result, not Guess mode's compound one.

**Remedy**

> Widen the engine contract's scoreAnswers return type to something mode-opaque (e.g. Record<playerId, unknown>, with each mode's scoring detail typed at its own call site the same way round/answers already are), or otherwise define a shape that can hold Guess mode's per-field correctness and three-way point breakdown.

### R3-2 — completeness

**Problem**

> The engine contract only specifies broadcasting via toPublicView(round, phase). It never describes how a player's submitted guesses (title text, artist text) or the scoreAnswers output (per-field correctness, point breakdown) reach clients for the reveal screen — Success Criteria requires the reveal to show exactly this data, but the contract as written broadcasts only the (redacted) round, not the answers or the scoring result.

**Remedy**

> Add to the engine contract sketch how/when submitted answers and scoreAnswers' output are delivered to clients at the results phase (e.g. the engine also broadcasts a per-mode toPublicResults(round, answers, scores) view, or scoreAnswers' output is folded into the same public-view mechanism).
